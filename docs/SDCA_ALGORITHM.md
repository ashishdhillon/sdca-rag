# Structure-Aware Document Chunking Algorithm (SDCA): Algorithmic Specification

## 1. Problem Definition
In standard Retrieval-Augmented Generation (RAG) systems, long documents such as academic research papers, reports, and manuals must be partitioned into compact segments (chunks) prior to dense embedding generation and vector indexing. Existing conventional chunking techniques (fixed token windowing, recursive splitting, and sentence grouping) operate almost exclusively on raw text streams. In doing so, they disregard document layout, typographical hierarchy, and structural boundaries. This leads to:
1. **Mid-sentence and mid-paragraph cleavage**: Chunks cleaving natural thematic discourse units.
2. **Heading detachment**: Section titles separated from their respective content bodies into disparate chunks.
3. **Semantic context dilution**: Chunks mixing content from unrelated sections across arbitrary token boundaries.

---

## 2. Motivation
Academic and structured PDF documents are inherently hierarchical. Authors organize ideas using typographical conventions: major section headers are distinguished by larger font sizes and bold weights, subsections introduce structured sub-arguments, and paragraphs frame single conceptual ideas. When a RAG system discards this structure, the retrieval model is forced to index fragmented context windows. By retaining structural boundaries deterministically at chunking time, retrieved passages preserve topical self-containment without requiring expensive neural chunkers or LLM pre-processing.

---

## 3. Research Objective
To design, implement, and validate **SDCA (Structure-Aware Document Chunking Algorithm)**, a deterministic, rule-based chunking algorithm for PDF documents that:
- Detects section and heading boundaries using layout geometry and font typography extracted via PyMuPDF.
- Preserves paragraph coherence and binds headings directly to their corresponding content.
- Targets approximately 400 tokens per chunk within a preferred working budget of 200–600 tokens.
- Decomposes oversized paragraphs strictly at natural sentence boundaries without word truncation.
- Operates 100% deterministically with zero embedding or neural model dependencies during chunk creation.

---

## 4. Input Representation
SDCA consumes the structured PDF data model generated by the Phase 1 extraction foundation (`Document`, `Page`, `TextBlock`, `TextSpan`):
$$\text{Document} = \{ P_1, P_2, \dots, P_N \}$$
Each page $P_i$ contains an ordered sequence of blocks:
$$P_i = \{ B_1, B_2, \dots, B_M \}$$
Each text block $B_j$ contains coordinates $\text{bbox} = (x_0, y_0, x_1, y_1)$, ordinal reading order `block_id`, assembled text, and styling spans:
$$B_j = \{ \text{spans}: [S_1, S_2, \dots, S_K] \}$$
where span $S_k$ provides font name, point size, flags (bold/italic bitmask), and color.

---

## 5. Structural Signals
SDCA computes and evaluates the following layout and typographical signals:
1. **Modal Body Font Size ($S_{\text{body}}$)**: The character-length-weighted modal font size of running body text across the document.
2. **Prominence Ratio ($R_{\text{size}}$)**: $\frac{\max_{S \in B}(\text{font\_size}(S))}{S_{\text{body}}}$.
3. **Styling Flags**: Presence of bold bitmasks (`flags & 4` or `flags & 16` or `'bold'` in font identifier).
4. **Brevity Constraint**: Total words $\le 25$ and total characters $\le 160$.
5. **Pattern Signals**:
   - Numbered academic heading regex (`r"^(?:(?:Section|Chapter)\s+\d+[:.]?|(?:\d+\.)+\d*|[IVXLCDM]+\.)\s+[A-Za-z]"`).
   - Canonical academic section titles (`Abstract`, `Introduction`, `Methodology`, `Results`, `Conclusion`, `References`, etc.).
6. **Margin & Stamp Exclusion**: Exclusion of headers/footers in the extreme 5% vertical margins, page numbers, email addresses, and repository stamps (`arXiv:\d+`).

---

## 6. Heading Detection Rules
A text block $B$ is classified as a section heading if and only if:
1. It is a text-type block (`block_type == 0`) with non-empty text.
2. Its length satisfies brevity: $\text{len}(\text{words}) \le 25$ and $\text{len}(\text{text}) \le 160$.
3. It does not fall in margin-excluded header/footer zones.
4. It is not an email address, copyright grant, or repository watermark stamp.
5. It satisfies at least one positive structural criterion:
   - **Criterion A (Numbered Heading)**: Matches canonical numbered prefix.
   - **Criterion B (Canonical Title)**: Matches known academic section taxonomy.
   - **Criterion C (Font Size Prominence)**: $\max(\text{font\_size}) \ge 1.15 \times S_{\text{body}}$, and does not end with full-stop sentence punctuation.
   - **Criterion D (Bold Prominence)**: Is bold and $\max(\text{font\_size}) \ge 1.05 \times S_{\text{body}}$, and does not end with full-stop sentence punctuation.

---

## 7. Section Construction
The document stream is parsed into sequential `Section` objects:
$$\text{Section} = \langle \text{heading}, \text{heading\_block\_id}, [\text{Paragraph}_1, \dots, \text{Paragraph}_k], \text{page\_start}, \text{page\_end} \rangle$$
- When a heading block is encountered, the prior active section is finalized and a new section is initiated.
- Subsequent non-heading blocks are ingested as body paragraphs.
- Text preceding the initial heading is captured as a preamble section ($\text{heading} = \text{None}$).
- Orphaned consecutive headings are merged as hierarchical paths (e.g., `2. Methodology - 2.1 Models`).

---

## 8. Chunk Assembly
For each constructed section:
1. **Oversized Paragraph Normalization**: Any paragraph with token count $> \text{max\_tokens}$ (600) is split at sentence boundaries into sub-paragraphs $\le \text{max\_tokens}$.
2. **Context Binding**: The detected section heading is prepended to the initial chunk of the section:
   $$\text{Chunk}_0.\text{text} = \text{Heading} + \verb|"\n\n"| + \text{Paragraph}_1 + \dots$$
3. **Greedy Paragraph Accumulation**: Successive paragraphs are accumulated as long as:
   $$\text{current\_tokens} + \text{tokens}(P_{k+1}) \le \text{max\_tokens}$$
4. **Boundary Preservation**: Paragraphs are not split mid-paragraph unless the paragraph independently exceeds $\text{max\_tokens}$.

---

## 9. Small-Section Handling
- If a section or paragraph has token count $< \text{min\_tokens}$ (200 tokens):
  - **Within Section**: A tail chunk with $< \text{min\_tokens}$ merges with the previous chunk in the same section if $\text{tokens}_{\text{prev}} + \text{tokens}_{\text{tail}} \le \text{max\_tokens}$.
  - **Preamble Content**: Headless introductory preambles $< \text{min\_tokens}$ merge with the subsequent section.
  - **Distinct Major Sections**: Distinct top-level sections (e.g., `4. Results` and `5. Conclusion`) are **never merged** across section boundaries simply to meet token quotas. Structural boundaries take precedence over arbitrary size targets.

---

## 10. Oversized-Content Handling
1. **Paragraphs $> \text{max\_tokens}$**: Split into complete sentences using regex-based sentence segmentation. Sentences are grouped into units $\le \text{max\_tokens}$.
2. **Sentences $> \text{max\_tokens}$ (Extreme Edge Case)**: If an individual sentence contains no punctuation and exceeds 600 tokens, it is split at whitespace word boundaries. Individual words are never cleaved.

---

## 11. Metadata Preservation
Every resulting `Chunk` carries:
- `chunk_id`: Unique identifier formatted as `sdca_{index}`.
- `text`: Complete textual content including heading context.
- `page_start`: 1-based page number where chunk content begins.
- `page_end`: 1-based page number where chunk content ends.
- `token_count`: Deterministic token count computed via `RegexTokenizer`.
- `strategy`: Explicitly set to `"sdca"`.
- `section`: Exact detected section title (or `None`).
- `metadata`: Contains `target_tokens`, `min_tokens`, and `max_tokens` configuration.

---

## 12. Token Target
- **Target Size**: $\approx 400$ tokens.
- **Preferred Working Range**: $[200, 600]$ tokens.
- All boundaries are fully parameterizable via function arguments.

---

## 13. Determinism
Given identical input PDF structures and parameter configurations, SDCA produces 100% bit-identical chunks. The algorithm contains no random seeds, no multithreaded race conditions, and no stochastic model calls.

---

## 14. Pseudocode

```text
Algorithm: Structure-Aware Document Chunking Algorithm (SDCA)
Input: Document doc, target_tokens = 400, min_tokens = 200, max_tokens = 600, tokenizer
Output: List of Chunk objects

1.  token_counter ← get_token_counter(tokenizer)
2.  S_body ← ComputeModalBodyFontSize(doc)
3.  sections ← []
4.  curr_sec ← None

// Step 1: Structure Detection & Section Construction
5.  for each page in doc.pages do:
6.      for each block in page.blocks do:
7.          if block.block_type ≠ TEXT then continue
8.          is_hd, title ← IsHeading(block, S_body, page)
9.          if is_hd then:
10.             if curr_sec ≠ None then append curr_sec to sections
11.             curr_sec ← NewSection(heading=title, page_start=page.number)
12.         else:
13.             para ← NewParagraph(text=block.text, page_number=page.number)
14.             if curr_sec == None then:
15.                 curr_sec ← NewSection(heading=None, page_start=page.number)
16.             append para to curr_sec.paragraphs
17. if curr_sec ≠ None then append curr_sec to sections

// Step 2: Chunk Assembly within Sections
18. raw_chunks ← []
19. for each sec in sections do:
20.     normalized_paras ← []
21.     for each p in sec.paragraphs do:
22.         if p.tokens > max_tokens then:
23.             normalized_paras.extend(SplitOversizedParagraph(p, max_tokens))
24.         else:
25.             normalized_paras.append(p)
26.     
27.     curr_paras ← []
28.     curr_tokens ← 0
29.     is_first ← True
30.     h_tokens ← token_counter(sec.heading) if sec.heading else 0
31.     
32.     for each p in normalized_paras do:
33.         prefix_tok ← h_tokens if (is_first and curr_paras is empty) else 0
34.         if curr_tokens + p.tokens + prefix_tok ≤ max_tokens then:
35.             append p to curr_paras
36.             curr_tokens ← curr_tokens + p.tokens + prefix_tok
37.         else:
38.             chunk_text ← FormatText(curr_paras, sec.heading if is_first else None)
39.             append (chunk_text, curr_paras.page_start, curr_paras.page_end, sec.heading) to raw_chunks
40.             curr_paras ← [p]
41.             curr_tokens ← p.tokens
42.             is_first ← False
43.     if curr_paras is not empty then:
44.         chunk_text ← FormatText(curr_paras, sec.heading if is_first else None)
45.         append (chunk_text, curr_paras.page_start, curr_paras.page_end, sec.heading) to raw_chunks

// Step 3: Small-Chunk Merging & Finalization
46. merged_chunks ← []
47. for each item in raw_chunks do:
48.     if CanMergeCompatible(merged_chunks.last, item, min_tokens, max_tokens) then:
49.         merged_chunks.last ← Merge(merged_chunks.last, item)
50.     else:
51.         append item to merged_chunks
52. return [NewChunk(id=f"sdca_{i}", text, page_start, page_end, section, strategy="sdca") for i, item in enumerate(merged_chunks)]
```

## 15. Example Walkthrough

Consider a section extracted from an academic paper:
- **Heading**: `2. Proposed Methodology` (14.0 pt bold)
- **Paragraph 1**: Problem formulation text (180 tokens, 10.0 pt)
- **Paragraph 2**: Algorithmic pipeline text (190 tokens, 10.0 pt)
- **Paragraph 3**: Implementation considerations (120 tokens, 10.0 pt)

**Fixed Chunking Execution (Target 400, Overlap 50)**:
- Window 1 (Tokens 0–400): Takes heading + Paragraph 1 + Paragraph 2 + first 25 tokens of Paragraph 3. **Paragraph 3 is severed mid-sentence.**
- Window 2 (Tokens 350–494): Takes last 40 tokens of Paragraph 2 + remainder of Paragraph 3. Contains duplicate partial content without heading context.

**SDCA Execution (Target 400, Range 200–600)**:
- Chunk 1: Ingests `2. Proposed Methodology` + Paragraph 1 + Paragraph 2 + Paragraph 3.
  $$\text{Total Tokens} = 4 + 180 + 190 + 120 = 494 \text{ tokens}$$
  Because $494 \le 600$ (within preferred range), Paragraph 3 is preserved entirely in its native context.
  Output Chunk:
  ```text
  2. Proposed Methodology

  Problem formulation text...

  Algorithmic pipeline text...

  Implementation considerations...
  ```
  `section = "2. Proposed Methodology"`, `token_count = 494`, `page_start = 2`, `page_end = 2`.

---

## 16. Edge Cases Handled
1. **Missing or Non-Standard Headings**: Documents without font variation default to preamble grouping with paragraph preservation.
2. **Consecutive Orphaned Headings**: Successive headings without intermediate text (e.g. Chapter heading followed immediately by Section 1) are merged as contextual paths (`"Chapter 2 - 2.1 Overview"`).
3. **Oversized Paragraphs**: Long uninterrupted text blocks are split cleanly at sentence boundaries.
4. **Oversized Sentences**: Extreme run-on sentences without punctuation are split at whitespace boundaries without word cleavage.
5. **Multi-page Sections**: Page intervals (`page_start`, `page_end`) track sections spanning page boundaries accurately.
6. **Watermarks & Metadata**: ArXiv stamps and copyright disclaimers are filtered from heading candidacy.

---

## 17. Limitations
1. **Complex Multi-Column Flow**: On multi-column documents where PyMuPDF's natural reading order weaves between columns, block ordering depends on the underlying PDF stream order.
2. **Image-Embedded Text**: Scanned or vector-rasterized text without font metadata cannot be analyzed without OCR (excluded by scope).
3. **Table & Math Formatting**: Large multi-row tables are currently parsed as single blocks; fine-grained cell-level structural extraction is beyond the current scope.

---

## 18. Computational Complexity
- Let $N$ be the number of text blocks in the document ($N \le 10^4$ for typical papers).
- Let $M$ be the total number of characters.
- Font size modal frequency: $O(M)$ time using single-pass hash counter.
- Structure detection: $O(N)$ regex and bounding box checks.
- Paragraph normalization and assembly: $O(N + K)$ where $K$ is the number of sentences.
- **Overall Time Complexity**: $O(M)$, linear in document length.
- **Space Complexity**: $O(M)$ memory to store the document hierarchy and chunks.
- Highly efficient and suitable for fast, scalable pre-indexing pipelines.

---

## 19. SDCA Version 2 (SDCA V2): Hierarchical Context and Bound Headings

### 19.1 Motivation and Shortcomings of V1
While SDCA V1 demonstrated a 100% Hit@5 rate and strong semantic cohesion, empirical Phase 4 benchmark analysis revealed three specific structural optimization opportunities:
1. **Isolated Heading Fragments**: In V1, standalone headings could occasionally be emitted as tiny, low-information chunks (e.g., 12 tokens) if section transitions coincided with chunk boundaries.
2. **Loss of Ancestral Breadcrumb Context**: A subsection like `3.2.1 Multi-Head Attention` was treated as an isolated title string, losing the critical macro-context that it resides inside `3. Transformer Architecture`.
3. **Bi-Encoder Passage Bias**: Dense bi-encoders like `all-MiniLM-L6-v2` were pre-trained on dense semantic passages rather than broad section scopes, resulting in lower point-wise cosine similarity for broad chunks compared to compact sentence clusters.

### 19.2 V2 Architectural Enhancements
SDCA V2 introduces four targeted architectural improvements implemented in `src/sdca/v2/`:

1. **Heading-Content Binding**:
   Headings are strictly prohibited from forming standalone chunks. A detected heading is directly bound to its subsequent introductory paragraph or subsection body. If a heading has no immediate content (an "umbrella heading"), it is absorbed into the path of its first child subsection.

2. **Hierarchical Document Tree & Section Path**:
   A deterministic hierarchy stack tracks heading levels based on numbered notation (`1.` vs `1.1` vs `1.1.1`) and typographical prominence ($R_{\text{size}}$ and bold weight):
   - Level 1: Major Sections (`1. Introduction`, `3. Architecture`)
   - Level 2: Subsections (`3.1 Encoder`, `3.2 Attention`)
   - Level 3: Sub-subsections (`3.2.1 Scaled Dot-Product`)
   Every chunk records its ancestral path in metadata:
   ```json
   {
     "section_path": "3. Architecture > 3.2 Attention > 3.2.2 Multi-Head Attention",
     "parent_heading": "3.2 Attention",
     "heading_level": 3
   }
   ```

3. **Dual Representation: Clean Verbatim Text vs. Structure-Aware Retrieval Text**:
   - `chunk.text`: Clean, verbatim passage preserved strictly for user display, LLM prompt assembly, and citation.
   - `chunk.retrieval_text`: Prepends the hierarchical breadcrumb directly into the text passed to the embedding model:
     ```text
     [Section: 3. Architecture > 3.2 Attention > 3.2.2 Multi-Head Attention]

     Multi-head attention allows the model to jointly attend to information...
     ```
   This injects top-level document semantics into the dense embedding vector without contaminating generative prompt context.

4. **Hierarchical Small-Chunk Merging**:
   Small sibling subsections under the same parent section (e.g., small definition paragraphs $< 200$ tokens) are merged together under their shared parent heading up to the target token budget, while strictly preserving major Level 1 boundaries.
